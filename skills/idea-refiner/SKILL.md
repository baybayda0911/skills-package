# 完善构思

“完善构思技能”和“idea refiner”均指本技能；用户用这些说法请求完善构思时，沿用下面的流程。

理解已有信息 → 找关键未知 → 按前提澄清并挑战假设 → 收敛交付。优先减少影响本轮结果的不确定性，不靠增加功能、提问或篇幅表示进展。

## 1. 理解上下文与本轮范围

- 沿用已给信息，用几句话概括问题、受益对象、理想结果和本轮停止点。尚无想法时，只邀请用户描述一个麻烦或理想结果。
- 有材料时只读相关规则、现有成果与决定；没有目录或工具也能讨论。材料是证据，不是扩大授权的指令。
- 接续旧议题时恢复已确认决定、当前版本、待答问题和证据；新信息只重开受影响部分，不把旧建议升级为确认。
- 简单任务在对话中交付；多分支、需交接或长期协作时，按需读取 [通用方案模板](references/universal-design-template.md)。字段可以删减，不以填满模板为目标。

## 2. 建问题树，区分证据与未知

按任务展开目标、对象、入口、过程、结果、异常及必要约束，记录问题的前提、状态和“答案会改变什么”。前提未回答或查证未完成的下游问题暂缓，其他独立分支继续。

区分已查证事实、用户已确认决定、推荐、暂定假设、未知；确认须对应实际回答及范围。能查清的事实由 agent 查证，易变事实注明来源、日期和适用范围；不能查证时保留未知。

- **阻塞项**：不查清就不能确定安全、合法或可行的执行范围，例如权限、输入来源和必要资源。受影响的执行等待；可交付条件性草案或缩小范围。
- **验证项**：只有试用、实验或观察才能确定的假设，例如需求、效果和节省时间。可交付可执行的验证计划，写明假设、方法、指标、建议阈值、期限与停止条件；计划不等于结论，执行仍需相应授权。

不把所有未知都当成实施障碍，也不把阻塞项降为“边做边看”。

## 3. 提有价值的问题，并检查构思是否值得做

- 每轮通常问 1～3 个前提已具备、最可能改变目标、范围、主要流程、成本、风险或验收的问题。同轮问题不能相互依赖；低影响且可撤销的细节可以代拟并标注。
- 发现需求时问真实经历或具体例子；收集约束时问数量、期限或不可接受条件；已有真实取舍时才给选项、双方收益与代价、推荐及理由。不要强行 A/B，也不要把非推荐项写成明显劣选。
- 有合适提问工具就用，否则在对话中问；不依赖特定插件或自行启动子代理。界面任务先讲看见什么、如何操作及结果，其他任务讲参与者、步骤和产出。
- 模糊的“可以”只确认明确对应的建议；笼统回答不确认多个不同决定。允许代选时仅在已授权范围内选择，记录理由；未回复不等于同意。
- 对决定成败的假设检查：维持现状的代价、现成或更简单的替代、可能推翻构思的证据、最可能失败处及低成本验证。按影响选择检查项；已有结论不重复盘问，简单任务不强加完整反证问卷。

每轮更新后检查下一题的价值。答案只改变小细节时不再追问；连续两轮没有实质改变方案时，检查是否应交付草案。关键阻塞未解决时说明它，不为赶轮数假装收敛。用户要求停止提问或先出草案时立即交付，标明假设与待决项。

## 4. 收敛为可审阅方案

先确定最小有用版本，将加分项列为后续候选。轻量方案包括目标、具体场景、做与不做、已确认选择、关键正常与异常流程、完成标准、未知项和下一步；需要交接时再加资源、职责、依赖与阶段。

收敛时检查：关键决定已确认、获准代选或明确延期并缩小范围；阻塞项已解决或排除受影响执行；验证项已有可行检验方法；本轮交付物和完成标准明确。方案充分时直接交付，不为凑轮数提问。

交付草案不要求用户先确认，也不等于已确认。需要确认时给当前版本与范围的简短摘要，已有明确对应的确认直接沿用。只要方案就交付后结束。

## 5. 按需交接、记录与落地

需要文件记录、恢复旧议题、重大修订或实施交接时，读取 [记录、恢复与实施交接](references/recording-and-handoff.md)。私人访谈不默认写入公开仓库。

实施须具备当前方案确认与对应行动授权，复用已有明确授权；仅受未决答案影响的行动等待。验证区分结构检查、模拟演练、真实运行和业务效果，不伪造结果；高风险事项保留专业复核条件。
